# Backend Presentation Guide: Enterprise Compliance & Audit Intelligence Platform

This comprehensive guide breaks down the backend architecture, request flows, and AI components of the Compliance AI Platform. Use this document to prepare for your architecture presentation tomorrow.

## 1. Backend Architecture Overview

### Folder Structure & Responsibilities
The backend follows a modular, domain-driven structure using FastAPI.

- `app/main.py`: The application entry point. Handles FastAPI initialization, CORS middleware, global exception handling, database table verification, auto-schema migration, and bootstrapping the default admin user.
- `app/api/`: Contains the REST API endpoints. Grouped by version (v1) and domain (auth, documents, mcp, etc.). All routers are aggregated in `router.py`.
- `app/core/`: Application-wide configuration and utilities (`config.py` for environment variables, `security.py` for JWT/password hashing, `dependencies.py` for FastAPI Depends injections like `get_current_user`).
- `app/models/`: SQLAlchemy ORM models (`user.py`, `audit_report.py`, `compliance_violation.py`). Defines the relational database structure.
- `app/crud/`: Create, Read, Update, Delete abstractions. Isolates database query logic from API endpoints.
- `app/schemas/`: Pydantic models for request validation and response serialization.
- `app/services/`: Core business logic (`rag_service.py` for AI/ChromaDB, `compliance_service.py` for document analysis, `drive_upload_service.py`).
- `app/agents/`: LangGraph AI agents (`compliance_agent.py`, `risk_agent.py`, `report_agent.py`, `workflow.py`). Orchestrates multi-step reasoning workflows.
- `app/mcp/`: Model Context Protocol integrations (`google_drive.py`, `notion.py`, `local_files.py`) for syncing external knowledge sources.

### Request Lifecycle (API to DB Response)
1. **Client Request**: An HTTP request hits a FastAPI endpoint (e.g., `POST /api/v1/auth/login`).
2. **Middleware & Validation**: CORS headers are checked. Pydantic validates the request body against a Schema.
3. **Dependency Injection**: FastAPIs `Depends()` resolves requirements (e.g., extracting/validating JWT token to get `current_user`, injecting the `SessionLocal` database connection).
4. **Endpoint Handler**: The route function executes. It delegates complex tasks to the **Services Layer** or queries the DB via the **CRUD Layer**.
5. **Database Interaction**: SQLAlchemy translates Python objects into SQL queries, executes them against PostgreSQL/SQLite, and returns ORM model instances.
6. **Response Serialization**: The endpoint returns the result. FastAPI uses the `response_model` Pydantic schema to format the output as JSON and return it to the client.

## 2. API Layer Analysis

The API layer is versioned under `app/api/v1` and modularized.

### Major Routes
- **`auth.py`**: Authentication logic. Endpoints for `/register`, `/login`, `/refresh`, and `/me`.
- **`documents.py`**: Document ingestion and RAG QA.
  - `/upload`: Uploads a PDF/DOCX, saves locally, optionally uploads to Google Drive, extracts text, chunks it, and ingests it into ChromaDB.
  - `/ask`: Performs RAG QA against ingested documents.
  - `/analyze`: Runs a narrative compliance gap analysis.
- **`mcp.py`**: External integrations sync.
  - `/sync`: Syncs configured MCP sources (Google Drive, Notion).
  - `/google-drive/sync` & `/notion/sync`: Dedicated granular sync endpoints.
- **`workflow.py`**: Triggers the LangGraph multi-agent compliance audit workflow.

### Request/Response Flow
Requests pass through Pydantic validators (`app/schemas/`) which enforce strict typing. Responses are serialized back via `response_model`. For example, `POST /auth/login` expects `LoginRequest` schema and returns `TokenResponse` schema. 

### Authentication Flow
Protected routes use `Depends(get_current_user)`. This dependency reads the `Authorization: Bearer <token>` header, decodes the JWT, verifies expiration, and fetches the User from the database. If invalid, it raises an HTTP 401 Unauthorized exception.

## 3. Database Layer Analysis

The platform uses SQLAlchemy as the ORM to interact with the SQL database.

### SQLAlchemy Models
1. **User (`app/models/user.py`)**
   - **Responsibility**: Stores user identities, hashed passwords, and roles (`admin`, `auditor`, `compliance_officer`).
   - **Details**: Passwords stored as bcrypt hashes.
2. **AuditReport (`app/models/audit_report.py`)**
   - **Responsibility**: Stores the finalized compliance audit report generated by the LangGraph agents.
   - **Details**: Contains `risk` level, `compliance_score`, `violation_count`. Uses JSON-encoded text fields for `issues` and `recommendations` to ensure cross-database compatibility (SQLite/PostgreSQL).
3. **ComplianceViolation (`app/models/compliance_violation.py`)**
   - **Responsibility**: Structured representation of individual compliance gaps found during an audit.
   - **Relationships**: A one-to-many relationship where an `AuditReport` has many `ComplianceViolations`.

### CRUD Operations
The `app/crud/` directory houses singleton instances (like `crud_user`, `crud_audit_report`) that encapsulate SQLAlchemy `db.query()` logic. This keeps API endpoints clean and prevents SQL logic from bleeding into the presentation layer.

## 4. Authentication System

- **JWT Flow**: The app uses JSON Web Tokens (JWT). Upon successful `/login` (which verifies the bcrypt password hash), the server generates an `access_token` (short-lived) and a `refresh_token` (long-lived). 
- **Token Validation**: The `get_current_user` dependency uses the `python-jose` library to decode the JWT, verifying the secret key and `exp` (expiration) claim. It extracts the `sub` (user ID) to load the user profile.
- **Role-based Access Control (RBAC)**: Specific dependencies like `get_admin` wrap `get_current_user` and enforce that `user.role == UserRole.ADMIN`, restricting endpoints like MCP sync to administrators.

---

## 5. MCP Layer (Model Context Protocol)

The MCP layer integrates external knowledge repositories into the AI's context window.

- **Google Drive MCP (`google_drive.py`)**: Uses a Google Service Account (`.json` key). Performs recursive folder traversal to find PDFs and DOCXs. Features pagination (handles >100 files) and **incremental sync** (skips files already in ChromaDB by matching `drive_file_id`).
- **Notion MCP (`notion.py`)**: Connects to Notion databases using an API token. Extracts page text and ingests it.
- **Ingestion Flow**: Triggered via `/api/v1/mcp/sync`. For each configured source:
  1. Authenticate & fetch file metadata.
  2. Download file / fetch page content.
  3. Extract raw text.
  4. Chunk the text into smaller overlapping segments.
  5. Store in ChromaDB with provenance metadata (source, links, IDs).

---

## 6. Services Layer

The Services layer encapsulates core business logic independent of the web framework.

- **`rag_service.py`**: The heart of the AI system. Handles ChromaDB connections, text extraction (`pdfplumber`, `pytesseract` OCR fallback, `pypdf`, `python-docx`), text chunking (sliding window), embeddings/storage, and retrieval context building for the LLM (Ollama/Llama3).
- **`compliance_service.py`**: Generates unstructured narrative compliance analysis by comparing policy chunks against regulation chunks using the LLM.
- **`drive_upload_service.py`**: Handles pushing locally uploaded files up to a Google Drive backup folder, ensuring deduplication.

## 7. AI Layer

### RAG Architecture (Retrieval-Augmented Generation)
1. **Ingestion**: Documents are extracted, chunked (default 1000 chars, 200 overlap), and inserted into **ChromaDB**. 
2. **ChromaDB Usage**: Acts as the vector database. It converts text chunks into mathematical vectors (embeddings) and stores them along with rich metadata (`filename`, `document_type`, `drive_web_view_link`).
3. **Retrieval Process (`rag_service.retrieve_chunks`)**: When a question is asked, the query is vectorized. ChromaDB finds the closest chunks using cosine distance. The system intelligently detects target filenames in the query (e.g., "in the 2024 report") and applies metadata `$or` filters to constrain retrieval.
4. **Source Attribution**: The chunks passed to the LLM include exact headers: `[File Name: X | Page Number: Y | Chunk ID: Z]`. The LLM is strictly instructed to cite these sources in its answer.
5. **Trend Analysis/Comparison Mode**: If the query mentions multiple files and comparison keywords ("compare", "vs", "trend"), the retrieval strategy changes. It guarantees a minimum number of chunks from *each* referenced file and instructs the LLM via a specific "comparison intent" system prompt to highlight differences and trends.

## 8. LangGraph Agents

The system uses `langgraph` to build autonomous, multi-step workflows representing a virtual audit team.

- **Graph Topology (`app/agents/workflow.py`)**:
  `retrieve_documents` -> `run_compliance_agent` -> `run_risk_agent` -> `run_report_agent` -> `persist_report`
- **State**: A typed dictionary (`WorkflowState`) passed between nodes. It holds the raw chunks, analysis outputs, and final report data.
- **The Agents**:
  1. **ComplianceAgent**: Analyzes the raw policy and regulation chunks to identify gaps and violations.
  2. **RiskAgent**: Takes the identified gaps, assesses their severity, classifies the risk level (Low, Medium, Critical), and proposes mitigation steps.
  3. **ReportAgent**: Synthesizes the outputs of the previous agents into a highly structured, professional final audit report JSON.
- **Execution**: Runs inside a `ThreadPoolExecutor` with a timeout. If LangGraph times out or fails, it falls back to a sequential execution of the node functions to guarantee a response.

## 9. End-to-End Request Examples

### A. User Login
1. **Request**: `POST /api/v1/auth/login` with email and password.
2. **Files**: `app/api/v1/auth.py`, `app/crud/user.py`, `app/core/security.py`.
3. **Database**: Queries `users` table for email.
4. **Functions**: `verify_password()` compares hashes. `create_access_token()` generates JWT.
5. **Response**: JSON containing `access_token` and `refresh_token`.

### B. Upload Document
1. **Request**: `POST /api/v1/documents/upload?document_type=policy` (multipart/form-data).
2. **Files**: `app/api/v1/documents.py`, `app/services/rag_service.py`, `app/services/drive_upload_service.py`.
3. **Flow**: Validates PDF -> Saves locally to `/uploads` -> Pushes to Google Drive (if configured) -> Extracts text -> Chunks text -> Stores in ChromaDB with metadata.
4. **Database**: ChromaDB (Vector store).
5. **Response**: `UploadResponse` showing chunk count, character count, and Drive link.

### C. Ask Question
1. **Request**: `POST /api/v1/documents/ask` with `{"question": "What is the data retention policy?"}`.
2. **Files**: `app/api/v1/documents.py`, `app/services/rag_service.py`.
3. **LLM/DB**: Queries ChromaDB for top ~10 relevant chunks. Passes chunks + question to Ollama (Llama 3).
4. **Functions**: `retrieve_chunks()`, `generate_answer()`.
5. **Response**: The LLM's answer with explicit bracketed citations.

### D. Compare 2020_Annual_Report and 2024_Annual_Report
1. **Request**: `POST /api/v1/documents/ask` with `{"question": "Compare the risks in 2020_Annual_Report and 2024_Annual_Report"}`.
2. **Flow**: `retrieve_chunks()` detects the two filenames. It queries ChromaDB with specific `where` clauses to fetch guaranteed chunks from *both* 2020 and 2024 reports. It sets `comparison_mode=True`.
3. **LLM**: `generate_answer()` uses the comparison system prompt.
4. **Response**: A structured comparison highlighting differences, additions, and trends between the two documents.

### E. Generate Trend Analysis (Audit Workflow)
1. **Request**: `POST /api/v1/workflow/run`.
2. **Files**: `app/api/v1/workflow.py`, `app/agents/workflow.py`.
3. **Flow**: 
   - `retrieve_documents`: Pulls all policy and regulation chunks.
   - `run_compliance_agent`: LLM finds gaps.
   - `run_risk_agent`: LLM assigns risk.
   - `run_report_agent`: LLM formats report.
   - `persist_report`: Saves to SQLite/PostgreSQL.
4. **Response**: The structured Final Report JSON containing risk scores and violations.

## 10. Presentation Preparation

### A. 5-Minute Explanation (Executive Pitch)
"This is an autonomous Compliance AI platform. The backend is built on FastAPI and Python. It ingest documents via direct uploads or syncing with Google Drive and Notion. We extract the text, chunk it, and store it in a ChromaDB vector database. When a user asks a question or runs an audit, we use Retrieval-Augmented Generation (RAG) to pull the exact relevant paragraphs and feed them to a local Llama 3 model. The true power is our LangGraph multi-agent system, which simulates a team of auditors (Compliance, Risk, and Reporting agents) passing data to each other to generate a finalized, mathematically scored audit report."

### B. 10-Minute Explanation (Technical Flow)
*Add to the 5-minute pitch:* "Let's talk architecture. We have a strict separation of concerns. Endpoints in our API layer handle HTTP and validation via Pydantic. They pass off to the Services layer, where `rag_service` manages ChromaDB and OCR fallbacks via pytesseract, and the Agents layer, which handles LLM orchestration. Our database layer uses SQLAlchemy to store structured audit histories and users in PostgreSQL, while ChromaDB handles the unstructured vector search. We built custom metadata filtering so the AI can do side-by-side document comparisons by dynamically querying specific file IDs."

### C. 15-Minute Explanation (Deep Dive)
*Add to the 10-minute pitch:* "For security, we implement strict JWT authentication and Role-Based Access Control. A standard user cannot trigger an MCP sync. When syncing with Google Drive, we use Service Accounts and recursive pagination, ensuring we skip duplicate files using an incremental sync strategy based on `drive_file_id`. In our AI layer, if LangGraph ever stalls, our orchestration script catches the timeout and falls back to sequential function execution, ensuring the API always returns a reliable response. Every AI response is strictly grounded with bracketed source citations mapping exactly to the ChromaDB chunk metadata."

### D. Likely Viva Questions
1. **Why use FastAPI instead of Django/Flask?**
2. **How does RAG prevent hallucinations?**
3. **Why use LangGraph instead of a single massive LLM prompt?**
4. **How do you handle very large PDFs?**
5. **What happens if Google Drive has 1000 files in subfolders?**

### E. Model Answers
1. **FastAPI**: It's asynchronous by default, incredibly fast, and auto-generates Swagger UI docs using Pydantic, which gives us strict type safety for our API boundaries.
2. **RAG/Hallucinations**: The LLM is given a strict system prompt: "Answer using ONLY the provided context." It is forced to append metadata citations `[File Name... Page...]` to every claim, tying its output mathematically back to the ChromaDB vector search results.
3. **LangGraph**: Breaking the task into Compliance -> Risk -> Report agents allows us to use specialized prompts for each step. It reduces cognitive load on the LLM, makes debugging easier (we can see the intermediate state), and produces much higher quality structured output.
4. **Large PDFs**: We extract text and split it into 1000-character chunks with a 200-character overlap (to preserve sentence context). The LLM never reads the whole PDF at once; it only reads the top 10 most semantically relevant chunks.
5. **Google Drive Pagination**: Our MCP script uses `nextPageToken` loops and maintains a `visited_folders` set to prevent circular traversal. It processes files recursively without hitting API limits.
